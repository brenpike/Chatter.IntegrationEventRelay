Integration Event Relay

Chatter.IntegrationEventRelay

Relays changes to a legacy SQL Server database's tables to message broker infrastructure as integration events, so systems that can't publish events themselves can take part in an event-driven architecture.

  • MIT license
  • .NET 10 (net10.0)
  • Runs in a .NET Worker Service
  • Tested on SQL Server 2019 and 2022
Start with the quick start See how it works

01 · The problem

Legacy systems write rows. They can't publish events.

Legacy systems write to a SQL Server database but can't create or publish integration events. Their as-is architecture, technical debt, or inability to integrate with message broker infrastructure keeps them out of an event-driven architecture.

  • A monolithic desktop app (WinForms or Swing)
  • A VBA Excel app
  • People editing tables directly

The relay doesn't ask them to change. It watches their tables instead. The one requirement: the legacy backend is SQL Server.

02 · Mapping

From row change to integration event

Six steps. The mapper is the only part you write.

  1. A change source watches the tables

    It watches tables for row changes: an insert, update or delete of one row.

  2. Each row change becomes a source event

    A source event holds the row's values, typed by the mapping's source event type.

  3. A mapping pairs table, change type and types

    A mapping in configuration pairs a table and change type with a source event type and an integration event type. Each mapping has exactly one mapper.

  4. The mapper decides

    The mapper is your code. It decides whether the source event becomes an integration event and builds it. Return null and nothing is published. For updates it sees OldValue and NewValue.

  5. The relay publishes through your broker

    It publishes integration events through any Chatter message broker infrastructure implementation, such as Azure Service Bus. [BrokeredMessage("order-shipped-event")] names the topic; consumers subscribe.

  6. Configuration is checked at startup

    The relay checks its configuration when the host starts and stops with a list of problems.

Running example. The Orders table. When OrderStatus changes to Shipped, the mapper publishes OrderShippedEvent to the order-shipped-event topic.

03 · Change sources

Two change sources. One per table.

One relay can use both change sources, but each table uses only one. Each mapping names its source.

Tested against SQL Server 2019 and 2022.

SQL Service Broker

  • A trigger on each watched table, in the writing transaction, adds modified rows to a Service Broker queue. The Worker consumes it.
  • Needs SQL Server with Service Broker (most PaaS offerings don't support it).
  • No CDC capture latency.
  • Order not guaranteed. Chatter generates the message id. Capabilities: None.
  • After downtime, changes wait in the queue.

CDC

  • The Worker polls the change tables that CDC's capture job fills from the transaction log. No trigger on the table.
  • Commit order per table (capture instance); no order across tables. Keeps the before-image of updates.
  • Resumes from a checkpoint while changes are still in the change table (retention default 3 days).
  • Commit time available (RelayContext.CommittedAt). The capture job scans the log every 5 s by default.
  • Needs SQL Server Agent, sysadmin to enable CDC on the database, db_owner per table.
  • Capabilities: Ordered, Resumable, CommitTime (ParkRow drops Ordered).

Delivery semantics

Aspect SQL Service Broker CDC
Capture Trigger in the writing transaction Capture job reads the transaction log
Order Not guaranteed Commit order per table (capture instance); no order across tables
Delivery At least once (Chatter's receive transaction and recovery options) At least once: a batch is checkpointed only after every change in it is published
Message id Generated by Chatter Derived from the source name, the change's position and the integration event type, so a replay republishes the same ids
Commit time (RelayContext.CommittedAt) Not available Available
Capabilities None Ordered, Resumable, CommitTime (ParkRow drops Ordered)
After downtime Changes wait in the queue Resumes from the checkpoint while the changes are still in the change table

Which one?

Use CDC when

  • mappers compare old and new values or depend on the order of changes (for example soft delete followed by restore), since CDC delivers each table's changes in commit order and keeps the before-image of every update;
  • you can't, or don't want to, add triggers to the legacy system's tables, or the writes must not pay for a trigger and a Service Broker send;
  • the relay must resume where it stopped after downtime, from changes still in the change table.

Use SQL Service Broker when

  • SQL Server Agent isn't available (CDC's capture job needs it), or CDC can't be enabled on the database;
  • changes must reach the relay without CDC's capture latency (the capture job scans the log every few seconds by default);
  • the table is already relayed this way and works as needed.

A mapping can require capabilities with RequiredCapabilities (for example "Ordered" or "Ordered, CommitTime"); the relay stops at startup if the mapping's source doesn't provide them.

04 · Reliability

At least once, and safe to replay

Both sources deliver at least once. SQL Service Broker acknowledges by committing Chatter's receive transaction once processing succeeds; Chatter's recovery options retry failures.

The checkpoint pin

  • With CDC, a batch is checkpointed only after every change in it is published.
  • After a crash the batch is republished with the same message ids, derived from the source name, the change's position and the integration event type.
  • Enable duplicate detection on topics (Azure Service Bus) or make consumers idempotent.

The lease

Several relay instances can run with the same configuration. A lease (a SQL Server application lock) lets one of them poll each capture instance while the others stand by.

Error policy

Transient failures are retried with exponential backoff and never parked. For a change that keeps failing with other errors, a CDC source applies its error policy.

Halt (default)

Stops at the change and keeps retrying. Nothing after it is published, so order holds.

ParkRow

Parks the change in <Schema>.Chatter_RelayParkedChanges after MaxAttemptsBeforePark attempts. Later changes to the same row park behind it; other rows carry on. On request, a replay republishes the row's parked changes in order.

Metrics and health check

Meter Chatter.IntegrationEventRelay.Cdc, with these instruments:

  • chatter.relay.cdc.changes
  • chatter.relay.cdc.parked
  • chatter.relay.cdc.batch.failures
  • chatter.relay.cdc.batch.duration
  • chatter.relay.cdc.lag
  • chatter.relay.cdc.parked.current

Tested SQL scripts enable CDC and grant the relay's login least-privilege permissions. The integration tests run the relay under exactly those grants.

05 · Switch-over

Switch a table between sources. One source relays each change.

.scripts/cdc/switch-to-cdc.sql and .scripts/cdc/switch-to-service-broker.sql switch a table between sources.

  • Each script picks a switch point. The source you switch away from relays every change committed before it; the source you switch to relays every change committed after it.
  • Every change is relayed by only one of the two sources, and each source is still at least once.
  • The switch commits in one transaction, or the script rolls all of it back and changes nothing.
  • The script locks the table, so writes to it pause until the script ends, normally a few seconds. Its waits for the relay, the capture job and the CDC sources end within about @timeoutSeconds (default 300); past it, the script rolls back and changes nothing. Some reads, the checks before the lock and, switching back, SqlChangeFeed's install procedures and the table's triggers aren't bounded by @timeoutSeconds. If the script doesn't finish, cancel it: that rolls it back too.
  • Mappers don't change.
  • Integration tests run both scripts in both directions.
