Chatter.IntegrationEventRelay

Integration Event Relay

Relays changes to a legacy SQL Server database's tables to message broker infrastructure as integration events, so systems that can't publish events themselves can take part in an event-driven architecture.

  • MIT license
  • .NET 10 (net10.0)
  • Runs in a .NET Worker Service
  • Author: Brennan Pike
  • $ man readme#quick-start
  • $ open github

The relay log lines use the relay's two real log templates. The OrderShippedEvent body shows the fields of the README's quick start.

$ why: the problem the relay solves

Legacy systems write to a SQL Server database but can't create or publish integration events. Their as-is architecture, technical debt, or inability to integrate with message broker infrastructure keeps them out of an event-driven architecture.

  • A monolithic desktop app (WinForms/Swing)ERR cannot publish events
  • A VBA Excel appERR cannot publish events
  • People editing tables directlyERR cannot publish events

REQUIRESThe legacy system's backend must be SQL Server.

The relay watches those tables for row changes and publishes them as integration events, so these systems can take part without publishing anything themselves.

  1. A change source watches tables for row changes (an insert, update or delete of one row).
  2. Each row change becomes a source event: the row's values, typed by the mapping's source event type.
  3. A mapping in configuration pairs a table and change type with a source event type and an integration event type. Each mapping has exactly one mapper.
  4. The mapper is your code. It decides whether the source event becomes an integration event and builds it. It returns null and nothing is published. For updates it sees OldValue and NewValue.
  5. The relay publishes integration events through any Chatter message broker infrastructure implementation, such as Azure Service Bus. [BrokeredMessage("order-shipped-event")] names the topic, and consumers subscribe.
  6. The relay checks its configuration when the host starts and stops with a list of problems.

Running example: in an Orders table, when OrderStatus changes to Shipped, the mapper publishes OrderShippedEvent to the order-shipped-event topic.

$ compare --sources: the two change sources

Two change sources are available. One relay can use both, but each table uses only one. Each mapping names its source in Source; a mapping without one uses SQL Service Broker.

CDCUse CDC when

  • mappers compare old and new values or depend on the order of changes (for example soft delete followed by restore), since CDC delivers each table's changes in commit order and keeps the before-image of every update;
  • you can't, or don't want to, add triggers to the legacy system's tables, or the writes must not pay for a trigger and a Service Broker send;
  • the relay must resume where it stopped after downtime, from changes still in the change table.

SSBUse SQL Service Broker when

  • SQL Server Agent isn't available (CDC's capture job needs it), or CDC can't be enabled on the database;
  • changes must reach the relay without CDC's capture latency (the capture job scans the log every few seconds by default);
  • the table is already relayed this way and works as needed.

STARTUPA mapping can set RequiredCapabilities. The relay stops at startup if the mapping's source doesn't provide them.

$ explain --delivery: delivery and reliability

AT LEAST ONCEBoth change sources deliver at least once, so a change can be published more than once. Plan for replays.

CDC

A batch is checkpointed only after every change in it is published. After a crash the batch is republished with the same message ids, derived from the source name, the change's position and the integration event type.

Enable duplicate detection on the topics (Azure Service Bus) or make consumers idempotent.

SQL Service Broker

Acknowledges by committing Chatter's receive transaction once processing succeeds. Chatter's recovery options retry failures.

Several relay instances

Several relay instances can run with the same configuration. A lease (a SQL Server application lock) lets one poll each capture instance while the others stand by.

Error policy

Transient failures are retried with exponential backoff and never parked. For a change that keeps failing with other errors:

HALTHalt (default)

Stops at the change and keeps retrying. Nothing after it is published, so order holds.

PARKParkRow

After MaxAttemptsBeforePark attempts the change is parked in <Schema>.Chatter_RelayParkedChanges, and later changes to the same row park behind it. Other rows carry on. On request, a replay republishes the row's parked changes in order.

Metrics and health check

Meter Chatter.IntegrationEventRelay.Cdc publishes:

  • chatter.relay.cdc.changes
  • chatter.relay.cdc.parked
  • chatter.relay.cdc.batch.failures
  • chatter.relay.cdc.batch.duration
  • chatter.relay.cdc.lag
  • chatter.relay.cdc.parked.current

TESTEDTested SQL scripts enable CDC and grant the relay's login least-privilege permissions. The integration tests run the relay under exactly those grants.

$ switch --help: switching a table between change sources

Two scripts switch a table between the change sources. Each picks a switch point.

Before the switch pointThe source you switch away from relays every change committed before it.
switch point
After the switch pointThe source you switch to relays every change committed after it.

Every change is relayed by only one of the two sources, and each source is still at least once.

  • ATOMICThe switch commits in one transaction, or the script rolls all of it back and changes nothing.
  • PAUSEThe script locks the table, so writes to it pause until the script ends, normally a few seconds. Its waits for the relay, the capture job and the CDC sources end within about @timeoutSeconds (default 300); past it, the script rolls back and changes nothing. Some reads, the checks before the lock and, switching back, SqlChangeFeed's install procedures and the table's triggers aren't bounded by @timeoutSeconds. If the script doesn't finish, cancel it: that rolls it back too.
  • MAPPERSMappers don't change.
  • TESTEDIntegration tests run both scripts in both directions.

$ install: packages and setup

Requires .NET 10 (net10.0) and SQL Server as the legacy system's database. The relay runs in a .NET Worker Service.

  • Chatter.IntegrationEventRelay

    Core: mapping configuration, mapper interfaces, and the processor that maps row changes to integration events and publishes them. It doesn't capture changes itself.

  • Chatter.IntegrationEventRelay.ServiceBroker

    The SQL Service Broker change source. It uses Chatter.SqlChangeFeed, which installs a trigger on each watched table that sends changed rows to a SQL Service Broker queue.

  • Chatter.IntegrationEventRelay.Cdc

    The CDC change source. It polls each capture instance's change table, hands the changes to the processor in commit order, and saves a checkpoint in the source database once a batch is published.

$ docker compose up --build: run the demo

From the root of the repo, docker compose up --build runs SQL Server, the Azure Service Bus emulator, two Worker Services and two Consumer Services. No Azure subscription needed.

100 database operations produce:

  • 50 Event1DeletedEvent (25 soft deletes and 25 hard deletes)
  • 25 Event1RestoredEvent
  • 25 Event2CreatedEvent

The demo uses both change sources: Event1 is captured with CDC, and Event2 with SQL Service Broker.
