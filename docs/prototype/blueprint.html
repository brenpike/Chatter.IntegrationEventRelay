Integration Event Relay

Chatter.IntegrationEventRelay

Relays changes to a legacy SQL Server database's tables to message broker infrastructure as integration events, so systems that can't publish events themselves can take part in an event-driven architecture.

One table, two ways to capture it. Choose a change source: its route energizes and its callouts appear. One relay can use both sources, but each table uses only one. The signal pulse follows the chosen route and stops with Pause animations.

Change source
  • SQL Service Broker route: dashed
  • CDC route: solid
  • Signal pulse: the chosen route
  • Numbered circles match the callouts

Route A: SQL Service Broker (dashed)

  1. 1
    Trigger in the writing transaction

    A trigger on each watched table adds the modified rows to a Service Broker queue, inside the transaction that wrote them.

  2. 2
    Order not guaranteed

    The Worker consumes the queue. Order is not guaranteed. There is no CDC capture latency.

  3. 3
    At least once

    Acknowledged by committing Chatter's receive transaction once processing succeeds; Chatter's recovery options retry failures.

Route B: CDC (solid)

  1. 1
    Log to change table

    CDC's capture job fills the change table from the transaction log, scanning the log every 5 s by default. No trigger on the table.

  2. 2
    Commit order per table

    The Worker polls the change table and hands changes on in commit order per capture instance, with no order across tables. A lease lock lets one instance poll.

  3. 3
    Checkpoint after publish

    A batch is checkpointed only after every change in it is published, so the relay resumes from the checkpoint after downtime.

  4. 4
    Stable message ids

    Derived from the source name, the change's position and the integration event type, so a replay republishes the same ids.

Signal path: how it works

Sheet
02 / 09
Scale
Not to scale

  1. Change source

    Watches tables for row changes: an insert, update or delete of one row.

  2. Source event

    Each row change becomes a source event: the row's values, typed by the mapping's source event type.

  3. Mapping

    A mapping in configuration pairs a table and change type with a source event type and an integration event type. Each mapping has exactly one mapper.

  4. Mapper

    Your code. It decides whether the source event becomes an integration event and builds it. Return null and nothing is published. For updates it sees OldValue and NewValue.

  5. Publish

    The relay publishes through any Chatter message broker infrastructure implementation, such as Azure Service Bus. [BrokeredMessage("order-shipped-event")] names the topic; consumers subscribe.

  6. Startup check

    The relay checks its configuration when the host starts and stops with a list of problems.

Each mapping picks a source: a named, configured instance of a change source.

Running example

The Orders table. When OrderStatus changes to Shipped, the mapper publishes OrderShippedEvent to the order-shipped-event topic.

  1. Orders row changes
  2. OrderStatus becomes Shipped
  3. Mapper builds OrderShippedEvent
  4. Topic order-shipped-event

Two change sources. One relay can use both, but each table uses only one. Each mapping names its source in Source; a mapping without one uses SQL Service Broker with the relay's ConnectionString.

Capabilities matrix: SQL Service Broker compared with CDC
Spec SQL Service Broker (dashed) CDC (solid)
CaptureTrigger in the writing transaction adds modified rows to a Service Broker queue.Capture job reads the transaction log into change tables; the Worker polls them. No trigger on the table.
OrderNot guaranteedCommit order per table (capture instance); no order across tables
DeliveryAt least once (Chatter's receive transaction and recovery options)At least once: a batch is checkpointed only after every change in it is published
Message idGenerated by ChatterDerived from the source name, the change's position and the integration event type, so a replay republishes the same ids
Commit timeNot availableAvailable (RelayContext.CommittedAt)
CapabilitiesNoneOrderedResumableCommitTime (ParkRow drops Ordered)
After downtimeChanges wait in the queueResumes from the checkpoint while the changes are still in the change table (retention default 3 days)
LatencyNo CDC capture latencyCapture job scans the log every 5 s by default
NeedsSQL Server with Service Broker (most PaaS offerings don't support it)SQL Server Agent; sysadmin to enable CDC on the database; db_owner per table

A mapping can require capabilities with RequiredCapabilities (for example "Ordered" or "Ordered, CommitTime"); the relay stops at startup if the mapping's source doesn't provide them. The relay is tested against SQL Server 2019 and 2022.

Tested SQL scripts enable CDC and grant the relay's login least-privilege permissions; the integration tests run the relay under exactly those grants.

Use CDC when

  • mappers compare old and new values or depend on the order of changes (for example soft delete followed by restore), since CDC delivers each table's changes in commit order and keeps the before-image of every update;
  • you can't, or don't want to, add triggers to the legacy system's tables, or the writes must not pay for a trigger and a Service Broker send;
  • the relay must resume where it stopped after downtime, from changes still in the change table.

Use SQL Service Broker when

  • SQL Server Agent isn't available (CDC's capture job needs it), or CDC can't be enabled on the database;
  • changes must reach the relay without CDC's capture latency (the capture job scans the log every few seconds by default);
  • the table is already relayed this way and works as needed.

Delivery and failure

Sheet
04 / 09
Scale
Not to scale
  • At least once

    Both sources deliver at least once. SQL Service Broker acknowledges by committing Chatter's receive transaction once processing succeeds; Chatter's recovery options retry failures.

  • Checkpoint after publish

    With CDC a batch is checkpointed only after every change in it is published. After a crash the batch is republished with the same message ids, derived from the source name, the change's position and the integration event type.

  • Duplicates

    Enable duplicate detection on topics (Azure Service Bus) or make consumers idempotent.

  • Transient failures

    Retried with exponential backoff and never parked.

Lease: one active, others standing by

Sheet
05 / 09
Scale
Not to scale

Several relay instances can run with the same configuration. A lease, a SQL Server application lock, lets one of them poll each capture instance while the others stand by.

The lock and the checkpoint belong to the source name and the capture instance.

  • ACTIVE

    Holds the lease and polls the capture instance.

  • STANDBY

    Stands by without polling. Standby instances are healthy.

Metrics are published on the meter Chatter.IntegrationEventRelay.Cdc (System.Diagnostics.Metrics), tagged with source and capture_instance. Collect them with OpenTelemetry (.AddMeter("Chatter.IntegrationEventRelay.Cdc")) or dotnet-counters.

Health check

The health check reports this instance's pollers.

Health check registration

services.AddHealthChecks().AddCdcChangeSource(maxLag: TimeSpan.FromMinutes(5));

It is unhealthy when a poller stopped on a gap, failed FailuresBeforeCritical times in a row, or lags more than maxLag; degraded while retrying a batch or while changes are parked. Standby instances are healthy.

Switch-over: flipping a table's route

Sheet
07 / 09
Scale
Not to scale

Two scripts switch a table between the change sources: .scripts/cdc/switch-to-cdc.sql and .scripts/cdc/switch-to-service-broker.sql. Each picks a switch point: the source you switch away from relays every change committed before it, the source you switch to relays every change committed after it.

Change committed

Before: the source you switch away from relays the change. The lever rests on the old route.

After: the source you switch to relays the change. The lever has flipped to the new route.

  • Only one source

    Every change is relayed by only one of the two sources. Each source is still at least once.

  • One transaction

    The switch commits in one transaction, or the script rolls all of it back and changes nothing.

  • Writes pause

    Writes to the table pause while the script runs, normally a few seconds. Past @timeoutSeconds (default 300) it rolls back.

  • Mappers unchanged

    Mappers don't change.

  • Tested

    Integration tests run both scripts in both directions.

Assembly instructions: try it

Sheet
09 / 09
Scale
Not to scale

The chain and package lines follow the Change source selector in the first sheet. Both are shown if your browser lacks :has().

  1. Add the packages

    dotnet add package Chatter.IntegrationEventRelaydotnet add package Chatter.IntegrationEventRelay.ServiceBrokerdotnet add package Chatter.IntegrationEventRelay.Cdcdotnet add package Chatter.MessageBrokers.AzureServiceBusdotnet add package Chatter.MessageBrokers.AzureServiceBus.Auth

  2. Wire up the relay in Program.cs

    Program.cs: SQL Service Broker chain

    // Wires up the mapper of each mapping in configuration
.AddIntegrationEventRelay()
    // Captures changes to the mapped tables with triggers and SQL Service Broker
    .UseServiceBrokerChangeSource();

    Program.cs: CDC chain

    .AddIntegrationEventRelay()
    .UseCdcChangeSource()
    .UseServiceBrokerChangeSource();

  3. Add a CDC source and mapping to appsettings.json

    appsettings.json

    "IntegrationEventRelay": {
  "ConnectionString": "...",
  "Schema": "Chatter",
  "Sources": {
    "orders-cdc": { "Type": "Cdc", "PollInterval": "00:00:01" }
  },
  "Mappings": [
    {
      "Source": "orders-cdc",
      "SourceEventTypeName": "MyNewIntegrationEventRelay.OrderChangedEvent",
      "IntegrationEventTypeName": "MyNewIntegrationEventRelay.OrderShippedEvent",
      "SourceChangeType": "Update",
      "TableName": "Orders",
      "TableSchema": "dbo",
      "CaptureInstance": "dbo_Orders"
    }
  ]
}

  4. Create the mapper

    OrderShippedMapper

    using Chatter.IntegrationEventRelay.Core.Abstractions;
using Chatter.IntegrationEventRelay.Core.Configuration;
using Chatter.IntegrationEventRelay.Core.Mapping;

namespace MyNewIntegrationEventRelay;

public class OrderShippedMapper : IMapSourceUpdateToIntegrationEvent<OrderChangedEvent, OrderShippedEvent>
{
    public Task<OrderShippedEvent?> MapAsync(MappingData<OrderChangedEvent> mappingData, RelayContext context, EventMappingConfigurationItem? mappingConfig)
    {
        OrderShippedEvent? orderShippedEvent = null;

        // mappingData.OldValue only has a value for an update
        if (mappingData.OldValue?.OrderStatus != "Shipped" && mappingData.NewValue?.OrderStatus == "Shipped")
        {
            orderShippedEvent = new OrderShippedEvent
            {
                Id = mappingData.NewValue.Id,
                CustomerId = mappingData.NewValue.CustomerId,
                ProductId = mappingData.NewValue.ProductId,
                OrderPlacedOn = mappingData.NewValue.OrderPlacedOn,
                OccurredAt = DateTime.UtcNow
            };
        }

        return Task.FromResult(orderShippedEvent);
    }
}

  5. Ship the seeded order

    Run the Worker Service with dotnet run, put a breakpoint on the mapper's return, then run:

    SQL

    USE [OrdersDB]
GO

UPDATE [dbo].[Orders]
   SET [OrderStatus] = 'Shipped'
 WHERE Id = '52CBE9FF-2496-4F46-9331-7F122AA3D973'
GO

    The mapper returns an OrderShippedEvent, which the relay publishes to the order-shipped-event topic.

Run the demo

The demo runs entirely in Docker: SQL Server, the Azure Service Bus emulator, two Worker Services and two Consumer Services. No Azure subscription is needed. From the root of the repo:

docker compose up --build

On startup the database is created and seeded, and 100 database operations are executed against it. The demo uses both change sources: Event1 is captured with CDC, Event2 with SQL Service Broker. The 100 operations produce:

  • 50Event1DeletedEventCDC, solid bar (25 soft deletes and 25 hard deletes)
  • 25Event1RestoredEventCDC, solid bar
  • 25Event2CreatedEventSQL Service Broker, dashed bar
